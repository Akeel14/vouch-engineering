- **Status:** Accepted
- **Date:** 2026-11-26
- **Deciders:** Vouch Engineering

## Context

`Vouch` is a multi-tenant two-sided sponsorship marketplace combining:

1. **Financial & Contractual Workflows:** Double-entry accounting (`ledger_entries`), two-tranche payout state machines, and strict tenant data isolation across brands and creators.
2. **Hybrid Creator Retrieval:** Lexical (`BM25`) and semantic (`512`-dimensional embedding) search across creator video transcripts paired with relational filters (median views, pricing, verification state).
3. **High-Concurrency Stateless Services:** Web BFF (`Next.js`), synchronous API workers (`FastAPI`), durable background workers, and an internal LLM gateway enforcing per-tenant request and token rate limits.

We need a repository layout and storage topology that enforce clear service boundaries, strong financial consistency, and parity between local development and managed AWS infrastructure without premature operational sprawl.

## Decision

### 1. Polyglot Monorepo Layout

All application, ML, and infrastructure code lives in a single versioned repository:

- `apps/web/`: `Next.js 15` (`React 19`, `TypeScript`, `Node.js 24 LTS`) managed via `pnpm` workspaces.
- `packages/contracts/` & `packages/evals/`: Shared API schemas and CI evaluation harnesses.
- `services/{api,worker,gateway}/`: `Python 3.12` (`uv`) services isolated by runtime role (stateless HTTP API, durable background worker, and internal LLM rate-limiting/routing gateway).
- `labs/ml-internals/`: Offline training and benchmarking (`XGBoost` anomaly scoring, `QLoRA` fine-tuning) isolated from production container dependencies.
- `infra/`: Database configuration and modular AWS `Terraform`.

### 2. Primary System of Record & Vector Store (`PostgreSQL 16` + `pgvector`)

`PostgreSQL 16` serves as the single transactional system of record for both relational entities and `pgvector` embeddings (`halfvec(512)` indexed with `HNSW`). All primary keys use time-ordered `UUIDv7`, monetary values are stored as `BIGINT` integer cents, and tenant-scoped tables enforce `FORCE ROW LEVEL SECURITY` (`RLS`).

### 3. Transaction-Mode Connection Pooling (`PgBouncer`)

All stateless application services connect through `PgBouncer` configured with `POOL_MODE=transaction` and `scram-sha-256` authentication rather than opening direct backend connections to PostgreSQL.

### 4. Ephemeral In-Memory State (`Redis 7` / `Valkey`)

`Redis 7` (`Valkey`-compatible wire protocol) is dedicated strictly to sub-millisecond ephemeral state: sliding/token-bucket rate limiters (`RPM` / `TPM`), short-TTL caches, and transient coordination. No source-of-truth business or financial records are stored in `Redis`.

## Alternatives Considered

- **Dedicated Vector Database (`Pinecone` / `Qdrant`):** Rejected for V1 (`< 10M` transcript chunks). Splitting relational metadata and vector indexes across two independent data stores introduces dual-write drift on account updates/deletions and prevents single-query execution of relational filters + `RLS` + vector similarity. Re-evaluate only if `HNSW` index memory competes with transactional `shared_buffers`.
- **Document Database (`MongoDB` / `DynamoDB`):** Rejected as primary store. Marketplace queries traverse entities bidirectionally (`organizations <-> campaigns <-> deals <-> creators`), double-entry accounting requires strict multi-row `ACID` invariants (`FOREIGN KEY` and `CHECK` constraints), and background job claiming relies on `SELECT ... FOR UPDATE SKIP LOCKED`. Variable platform metadata is stored in indexed `JSONB` columns where schema flexibility is needed.
- **Direct PostgreSQL Connections or Session Pooling:** Rejected. Holding backend PostgreSQL processes idle while awaiting external I/O (`Stripe`, social OAuth APIs, LLM providers) exhausts connection slots under burst traffic.

## Consequences

- **Operational Simplicity & Parity:** Local development runs `pgvector/pgvector:pg16`, `PgBouncer`, and `Redis 7` via `docker-compose.yml`, mapping via environment configuration (`DATABASE_URL`, `REDIS_URL`) to AWS `RDS PostgreSQL 16`, `PgBouncer / RDS Proxy`, and `ElastiCache (Valkey)` in production.
- **Transaction-Mode Pooling Invariants:** Because `PgBouncer` reassigns backend connections after each `COMMIT`, session-level PostgreSQL features (`SET` without `LOCAL`, session advisory locks, `LISTEN/NOTIFY`, and unguarded session prepared statements) must not be used on pooled connections. Tenant `RLS` context must always be set via transaction-scoped `SET LOCAL` inside explicit `BEGIN ... COMMIT` blocks.
- **Cache Disposability:** `Redis` is treated as non-durable; a full `Redis` flush or failover must degrade gracefully without affecting deal state or ledger integrity.
